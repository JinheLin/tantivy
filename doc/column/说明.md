# 专栏工作区说明（doc/column）

这是一套“边读源码边写专栏”的工作区：每篇文章一个 Markdown 文件，配套统一模板与 TODO，确保产出可复现、可迭代。

## 目录结构

- `doc/column/文章模板.md`：单篇文章模板（复制后改标题即可）
- `doc/column/第*部分-*/??-*.md`：文章草稿（按 Part 目录 + 编号命名）
- `doc/column_outline.md`：总大纲与进度表（勾选/状态更新）

## 写作约定（建议坚持）

- 每篇文章目标是“回答一个主问题”，不要在一篇里塞太多主题。
- 读代码“按调用链”：从 example/或公开 API 入口出发，逐层下钻。
- 每篇至少做 1 个实验并给出“验证点”（例如：输出包含哪些行/段数变化/查询命中数变化）。
- 代码引用尽量写清楚：
  - `路径 + 关键符号名`（比行号更稳定）
  - 必要时附带“在哪个模块里 re-export”帮助读者定位

## 常用命令（本地）

- 跑示例：`cargo run --example basic_search`
- 跑库与 tests：`cargo test --tests --lib`（也可 `make test`）
- 格式化：`make fmt`（需要 nightly）

## 发布前检查清单（每篇）

- [ ] 文章“主问题”一句话能说清楚
- [ ] 有可复现实验 + 读者能验证的输出/现象
- [ ] 关键入口文件清单齐全（按阅读顺序）
- [ ] 图或表至少 1 个（结构图/数据流/状态机/文件布局）
- [ ] FAQ ≤ 5 条，覆盖最常见疑问

## 适用范围

- **以源码为准**：文章内容以仓库当前源码行为为准；每篇文章开头会标注适用的 `tantivy` commit。
- **默认读者画像**：具备 Rust 基础；知道倒排索引、段（segment）、提交（commit）、删除（delete/tombstone）等基本概念。

- **代码片段**：
  - 使用 fenced code block，并注明语言（如 `rust`）。
  - 尽量保证片段可读、可迁移；如必须省略，使用 `// ...` 明确标注。

  - 优先引用“稳定入口”（类型/trait/API），并附上仓库相对路径链接到关键文件。

# 专栏说明

本目录 `doc/column` 用于记录对 **tantivy**（Rust 搜索引擎库）源码与实现细节的系列文章。文章以“读代码”为主线：尽量用代码里的真实结构、数据流和边界条件来解释行为与性能取舍。

## 写作约定

- **以代码为准**：本文中的结论以仓库中代码实现为依据；如与旧文档/旧博客冲突，以代码为准。
- **注明代码版本**：每篇文章开头给出 `tantivy @ <git short hash>`，避免不同版本细节差异导致误读。
- **路径即锚点**：涉及实现时，优先用仓库相对路径引用关键入口（例如 `src/postings/serializer.rs`），并尽量点出核心类型/函数名，便于读者定位。
- **中英文术语并列**：第一次出现时尽量写清楚（例如 Postings（倒排表/倒排列表）、Positions（位置）、FieldNorm（字段长度归一化）、Skip（跳表信息）、Block-WAND（块级动态剪枝）等）。
- **先讲“为什么”，再讲“怎么做”**：先回答“为什么要这样设计/存这些信息”，再展开数据结构与流程。
- **和 schema 配置相关的行为要说清楚**：尤其是 `IndexRecordOption`（Basic / WithFreqs / WithFreqsAndPositions）与 fieldnorm 开关对功能（短语查询）和性能（打分、剪枝）影响很大。

## 目录结构（建议）

- `doc/column/第1部分-.../`：基础概念与读代码准备。
- `doc/column/第2部分-写入管线/`：写入侧（索引构建）流程与文件格式。
- `doc/column/第3部分-查询与执行/`：查询解析、倒排访问、评分与剪枝。

## 文章模板

建议所有文章基于 `doc/column/文章模板.md` 开始，保持结构一致，便于按需跳读。
